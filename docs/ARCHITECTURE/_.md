# Architecture

Where code lives, who may use whom, how data is stored, and the rules that must not be broken. The stack is in the root `README.md`. How we work is in [Contributing](../CONTRIBUTING/_.md).

---

## Project structure

```
app/              pages, layouts, and route files only. No logic.
components/ui/    shadcn components. Never edited.
components/       shared UI built on shadcn.
db/               Drizzle schema and migrations.
server/           the shared engine: permissions, records, gates, audit log.
workbooks/wbNN/   one folder per workbook: its screens, actions, tool definitions, and tests.
lib/              small helpers.
e2e/              Playwright tests.
```

- Unit and integration tests sit next to the code they test, for example `check.ts` and `check.test.ts`.
- A tool definition is one TypeScript file with Zod in `workbooks/wbNN/tools/`.
- Pages stay Server Components. `"use client"` goes in the leaf component that needs it.

## Who may use whom

| Folder | May use | Never uses |
|---|---|---|
| `app/` | `workbooks/`, `components/`, `server/` | |
| `workbooks/wbNN/` | `server/`, `components/`, `db/`, `lib/` | another workbook |
| `server/` | `db/`, `lib/` | `workbooks/`, `app/` |
| `components/` | `lib/` | `db/`, `server/` |
| `db/` | nothing | everything else |

If two workbooks need the same thing, it moves into `server/` or `components/`. A lint rule enforces these directions in CI, so a PR that breaks them fails.

## Data model

Most of the tools (D1.1, D1.8, D2.4, and so on) share one generic record system. A record is stored with its project, tool ID, state, and a JSONB payload. Its state is `draft`, `submitted`, `approved`, `locked`, or `void`. A void record is kept for reference and audit, and can never be edited or moved again. The tool's Zod definition decides which fields it has, which are required, and which are inherited from an earlier tool.

An entity gets its own table when a dashboard totals it or filters on it across projects:

- people and their roles, held on one project or company-wide on every project (any role but Client)
- projects
- gates and approvals
- workbook rollbacks
- change requests
- the audit log
- contracts
- payments and invoices
- team capacity and assignments

Everything else stays in the generic system. An issue that adds a table says so in its description.

## Rules that must not be broken

1. **Gate order is never bypassed.** The server checks prerequisites before anything becomes active.
2. **Permissions are checked on the server only.** Hiding something in the UI is cosmetic.
3. **A locked record is immutable.** Only an approved change request unlocks it, or a workbook rollback by the project's PM, which reopens the target workbook as draft and voids every workbook after it.
4. **Every write is audited.** No write path skips the audit log.
5. **Inherited fields are never written by users.** The system fills them in.
6. **Production changes only through migrations.** Nobody edits it by hand.
