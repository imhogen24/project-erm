# Architecture

Where code lives, who may use whom, how data is stored, and the rules that must not be broken. The stack is in the root `README.md`. How we work is in [Contributing](../CONTRIBUTING/_.md).

---

## Project structure

```
app/              pages, layouts, and route files only. No logic.
components/ui/    shadcn components. Never edited.
components/       shared UI built on shadcn.
db/               Drizzle schema and migrations.
server/           the shared engine: permissions, records, workflow, audit log.
workbooks/wbNN/   one folder per workbook: its screens, actions, tool definitions, and tests.
lib/              small helpers.
e2e/              Playwright tests.
```

- Unit and integration tests sit next to the code they test, for example `check.ts` and `check.test.ts`.
- A tool definition is one TypeScript file with Zod in `workbooks/wbNN/tools/`.
- Pages stay Server Components. `"use client"` goes in the leaf component that needs it.

## Who may use whom

| Folder | May use | Never uses |
|---|---|---|
| `app/` | `workbooks/`, `components/`, `server/` | |
| `workbooks/wbNN/` | `server/`, `components/`, `db/`, `lib/` | another workbook |
| `server/` | `db/`, `lib/` | `workbooks/`, `app/` |
| `components/` | `lib/` | `db/`, `server/` |
| `db/` | nothing | everything else |

If two workbooks need the same thing, it moves into `server/` or `components/`. A lint rule enforces these directions in CI, so a PR that breaks them fails.

## Data model

Most of the tools (D1.1, D1.8, D2.4, and so on) share one generic record system. A record is stored with its project, tool ID, state, and a JSONB payload. Its state is `draft`, `submitted`, `approved`, `locked`, or `void`. A void record is kept for reference and audit, and can never be edited or moved again. The tool's Zod definition decides which fields it has, which are required, and which are inherited from an earlier tool.

People work a record through four steps in `server/records/records.ts`:

- `saveDraft` creates the record when the workflow has the tool open, or saves over its draft. The screen sends back the `updatedAt` of the record it opened. If someone else saved in between, the save is refused with `StaleRecordError`, which carries the newer record, and nothing changes. A draft can be saved incomplete.
- `submitRecord` checks required fields, copies in inherited values, and records `submitted_by` and `submitted_at`.
- `signField` writes who signed and when into a signature field. Only a person holding one of the roles the field names in `signedBy` may sign, and the registry refuses a signature field that names none. Signatures are never written through a payload. Editing any other field clears every signature, and the clearing is audited.
- `approveRecord` needs every signature field signed. It moves the record to `approved` and then `locked` in one transaction, so the next tool opens, and records `approved_by`, `approved_at` and `locked_at`. The person who submitted a record cannot approve it, even if they hold an approving role.

A change request reopens one locked record so it can be fixed. Anyone who may write the record's tool may ask, with a reason. Only the project's PM decides, and a rejection needs a reason too. A record has at most one open request at a time. A request moves through these statuses:

- `requested` when it is opened. The record stays locked.
- `approved` when the PM approves it. The record moves from `locked` to `draft` and can be edited.
- `rejected` when the PM rejects it. The record stays locked.
- `applied` when the reopened record is locked again through the normal submit, approve, and lock steps.

Records in later workbooks are not voided by a change request. The audit log marks each of them as built on a changed record instead.

### The workflow map

Which tools can start next is written as data in `server/workflow/`, one file per workbook (`wb01.ts`, `wb02.ts`, ...). For each workbook it says:

- when the workbook opens, and which service tracks use it. WB02 opens when D1.16 is locked, WB03 when D2.12 is locked, WB04 when D3.10 of the first payment milestone is locked, and WB05 when D4.8 is locked. Tier 3 projects skip WB05.
- for each tool, which tools must be locked before it can start (all of them, or any one), and an optional condition on a field of an earlier locked record, for example D1.2's triage decision is "Proceed to D1.3".
- which tools repeat once per payment milestone, where the number of milestones comes from, and which tool closes a cycle.
- hard stops: an answer on a locked record that ends the route and sets the project's status, for example D1.2 "Reject as Spam" sets `rejected`. No record is voided.

A workbook with no tool rules yet opens all its tools at once, and a workbook with no map opens none. Which track a tool is on, and the tool it replaces on the other track, come from the tool's definition. A Tier 3 project reads a wait for D1.8 as a wait for T3.D1.8a, which replaces it.

Only locked records count, so a draft never opens or stops anything. `availableTools(database, projectId)` returns the tools that can start now, each with the cycle its record gets, and `createRecord` refuses any other tool with an error that names what is still missing. A project has at most one record that is not void per tool and cycle, which a unique index enforces. A tool that does not repeat is always cycle 1.

`registerAllTools` checks the map against the registered tools: every tool, field and option a rule names must exist, so a typo fails at start-up. A map is checked once its workbook has a tool definition.

An entity gets its own table when a dashboard totals it or filters on it across projects:

- people and their roles, held on one project or company-wide (any role but Client). Only IT/Admin held company-wide gives access, on every project, since it assigns the team to each new one. Any other role held company-wide is a qualification: it records that the person can be assigned that role, and gives no access by itself. Access to a project comes only from being assigned to it, and removing a qualification leaves existing assignments as they are. One reserved person, "System" (`systemActor` in `server/system/`), is what automated jobs act as, such as the website intake creating D1.1. A migration creates it in every database. It has no account, holds no roles and cannot sign in, and database checks refuse any attempt. On records it skips only the permission check: the workflow map, the project status, validation and the state rules still apply, it can never approve or lock, and its writes are audited with it as the actor.
- projects, each with the website's request ID (unique, never edited), a service track (`Tier_1` or `Tier_3`, set at creation) and a status (`active`, `on_hold`, `rejected`, `closed` or `completed`). Only an active project can have records created, edited or moved; the others are read only. A status change needs the PM and a reason, and the audit log keeps both statuses and the reason on a line with no record.
- gates and approvals
- workbook rollbacks
- change requests
- the audit log
- contracts
- payments and invoices
- team capacity and assignments

Everything else stays in the generic system. An issue that adds a table says so in its description.

## Rules that must not be broken

1. **The workflow order is never bypassed.** The server checks the workflow map before a record is created.
2. **Permissions are checked on the server only.** Hiding something in the UI is cosmetic.
3. **A locked record is immutable.** Only two things unlock it: a change request approved by the project's PM, which moves that one record back to draft, or a workbook rollback by the project's PM, which reopens the target workbook as draft and voids every workbook after it.
4. **Every write is audited.** No write path skips the audit log.
5. **Inherited fields are never written by users.** The system fills them in.
6. **Production changes only through migrations.** Nobody edits it by hand.
