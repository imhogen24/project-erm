# Sign-up and provisioning

Who can make an account, and what each person sees before they are on a project.

## Two kinds of account

`people.account_type` is `client` or `staff`. It is set once, when the account is made, and never changes from the app.

- **Client**: made by the person at `/sign-up`.
- **Staff**: made only by accepting an IT/Admin invite (`/invite/[token]`).
- An invite whose only role is Client makes a client account. Any other role makes a staff account.

Existing people are backfilled: anyone with a company role, or a project role other than Client, is staff. Everyone else who holds a Client role is a client. Anyone with no role at all is staff, because only an invite could have made them.

## Client sign-up

1. `/sign-up` asks for name, email and password. It is open to everyone and makes only client accounts.
2. Better-Auth sends a link through `sendEmail` (email kind `verify_email`) and the page becomes `/verify-email`: check your email, send the link again.
3. Signing in before confirming is refused and sends a new link; the sign-in form opens `/verify-email`.
4. Opening the link confirms the email, signs the person in and attaches their website requests (below).

An email that already has an account gets the same answer as a new one, so sign-up never tells who has an account.

## Website requests attach by email

A website request carries the client's email. The client becomes Client on that project when:

- they verify an email that matches a request already pulled in, or
- a request is pulled in for an email that a verified client already has.

Matching ignores case. An unverified account never attaches, so nobody can claim a request by typing someone else's email.

## Staff

Invite only. Accepting an invite confirms the email, since the link reached the inbox. Public sign-up never makes a staff account, and an invite giving a staff role to a client account is refused, both when it is made and when it is accepted. A person who needs both uses a second email.

## What each person sees

| Person                            | Sees                                      |
| --------------------------------- | ----------------------------------------- |
| Email not confirmed               | No session: `/verify-email`               |
| Client, no project                | Your projects with only Start new project |
| Client, with projects             | Their projects and Start new project      |
| Staff, no project or company role | "You are not on any project yet."         |
| Staff, assigned                   | Their projects                            |

Start new project, and the action behind it, accept client accounts only (`isClientAccount` reads `account_type`).

## Email in tests

- Unit tests pass a fake transport and read the link from it.
- An email to a reserved test domain (`.test`, `.example`, `.invalid`, `.localhost`, `example.com/net/org`) is never handed to Resend, even with a real key. Seed people and browser tests use these domains.
- The link is a signed token that is never stored, so browser tests sign the same token with `BETTER_AUTH_SECRET` (`confirmLink` in `e2e/support/data.ts`).
