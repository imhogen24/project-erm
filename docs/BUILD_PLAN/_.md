# Build Plan

What gets built and in what order.

Related docs: [Contributing](../CONTRIBUTING/_.md) and [Architecture](../ARCHITECTURE/_.md).

---

## Approach

- **Foundation first, then vertical slices.** The foundation is the shared machinery every feature needs. A slice is one workbook built through schema, server actions, UI, and tests.
- **Issues are the specs.** Each Linear issue says what to build, links to the part of the system docs it implements, and lists the checks. 
- **Test-first.** The developer starts every issue by writing failing tests from its checks.

---

## Scope

The first target is **WB01 to WB05, Tier 1 only**:

| Workbook | Name |
|---|---|
| WB01 | Project onboarding |
| WB02 | Contract tracking and administration |
| WB03 | Payment scheduling and fund management |
| WB04 | Team assignment and capacity planning |
| WB05 | Standard engineering design (Tier 1 only) |

Not in scope for the first target: Tier 3 (drafting and digitization), and WB06 to WB13. They follow once this path works end to end.

## Order of work

### 1. Foundation

| Area | What it delivers |
|---|---|
| Developer setup | Docker Postgres, one-command setup, reset, seed data for every role |
| Test setup | The `erm_test` database, a standard way to write failing tests first |
| Sign-in and invites | Invite-only accounts, multiple roles, roles per project |
| Permissions | The matrix turned into server rules, tested table by table |
| Record system | Generic tool records with draft and locked states, tool definitions written in TypeScript with Zod, one file per tool |
| Gates and change requests | Approvals that unlock the next step, change requests that unlock a locked record, and workbook rollbacks that reopen an earlier workbook |
| Audit log | Append-only history of every change |
| App shell | Navigation, project list, and project overview, based on the wireframes |

File uploads and email are deferred to the first slice that needs them.

### 2. WB01 project onboarding

Built first, by the whole team, as the slice that sets the pattern. It exercises the intake job, the generic records, gates, and permissions. It is finished and reviewed before the team splits up.

### 3. WB02 to WB05

Built in parallel once WB01 has merged. Each slice follows the same shape:

1. Schema and permissions.
2. Server actions.
3. One issue per screen.
4. One Playwright flow for the happy path.

The issues for the next slice can be written while the current one is being built. That starts only when asked.

## Linear

- Issues sit in one flat list. Labels carry the workbook, the type, and the layer.
- Dependencies are Linear "blocked by" links.
- Logic and UI are separate issues. A UI issue has a **Design** field with a link to the design, is blocked by the logic issue it connects to, and is not started until the design link is filled in. This lets the people who know the screens work on the UI, and the people who know the server work on the logic.
- Issues are created one batch at a time. Each batch is drafted as a document, reviewed, and then created.
- Existing `RDP` issues are read first, and new issues build on them and do not duplicate finished work.
- Every issue uses the layout below. It will become a Linear issue template once the Linear connection is set up.

### Issue layout

An issue is written so that anyone on the team can pick it up without having seen the conversations behind it. It says what to build, in plain words, and lists the exact tests, so engineers do not have to guess.

| Field | What it holds |
|---|---|
| Title | A short action, for example "Add the invite flow for new staff" |
| Why this exists | Two to four plain sentences: what problem this solves and what depends on it |
| What to build | A short list of the things that must exist when the issue is done |
| Design | UI issues only. A link to the design (wireframe or Figma frame) that the engineer builds. Left empty until the design exists |
| System link | The part of the system docs the issue implements. The issue does not repeat it |
| Decisions already made | Choices that are settled, such as names, states, and libraries. The engineer follows these and does not choose again. A wrong decision is raised on the issue, not changed silently |
| Test cases | A table with one row per test: the scenario, what happens, and the expected result. Each row becomes one failing test written first |
| Done looks like | At most five checks written as given / when / then, as a summary of the test cases |
| Blocked by | Issues that must merge first |
| Labels | Workbook (`wb01`), type (`slice`, `foundation`), layer (`schema`, `ui`, `actions`, `e2e`) |
| Out of scope | What this issue deliberately does not cover, and which issue does |

The engineer may add tests beyond the table. The table is the minimum.
