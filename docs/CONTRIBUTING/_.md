# Contributing

How to get a change from a Linear issue to a merged PR. Setup is in the root `README.md`. Where code goes is in [Architecture](../ARCHITECTURE/_.md).

---

## The loop

Every change follows the same order: **issue, then failing tests, then code.**

- The Linear issue is the spec. It says what to build, links to the part of the system docs it implements, and lists the checks.
- You write the failing tests for those checks and commit them first.
- Then you write the code that makes them pass.

Do not invent behavior the issue and the system docs do not define. If something is unclear or missing, comment on the Linear issue and wait for an answer. The answer goes into the issue.

---

## Working an issue

1. Pick an issue that is not blocked, and read it and the section of the system docs it links to.
2. Branch from the latest `main`, using the branch name Linear generates:

   ```bash
   git switch main
   git pull origin main
   git switch -c <branch-name-from-linear>
   ```

3. Write the failing tests for the issue's checks, and commit them. A test usually imports code that does not exist yet, and the commit hook runs typecheck, so add an empty stub of that code first. The test then compiles and fails on its assertion.
4. Make them pass. The tests need the database running. `bun dev` starts it, or run `docker compose up -d --wait`. To run one file:

   ```bash
   bun run test path/to/file.test.ts
   ```

5. Before the PR, run these and fix what they report:

   ```bash
   bun run lint
   bun run typecheck
   bun run build
   bun run test
   bun run test:e2e
   coderabbit review
   ```

6. Open a PR against `main` with the Linear issue link, a short summary of the change, and numbered steps to test it.
7. Address review comments on the same branch. After it merges, pull `main` and do not reuse the branch.

Do not start work that is not on Linear.

**Testing rules.**

- Tests run against a Postgres database in Docker (`erm_test`), never against Neon and never against a mock. Neon is only for production.
- Tests sit next to the code they test, for example `check.ts` and `check.test.ts`.
- Browser tests (Playwright) go in `e2e/`.
