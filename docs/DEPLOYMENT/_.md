# Deployment

How the ERM runs in production. Setup for development is in the root `README.md`.

---

## Where it runs

- The app runs on Vercel.
- The database is Neon. The company website uses the same Neon database, so the ERM reads the website's intake tables directly. There is no webhook.
- Email is sent with Resend, from the verified company domain.

---

## Environment variables

Production does not use dotenvx. The values are plain variables in Vercel (Settings, Environment Variables), set for Production only:

| Variable             | What it is                                                           |
| -------------------- | -------------------------------------------------------------------- |
| `DATABASE_URL`       | The Neon connection string                                           |
| `BETTER_AUTH_SECRET` | A long random secret, different from development                     |
| `BETTER_AUTH_URL`    | The public address of the app, for example `https://erm.example.com` |
| `RESEND_API_KEY`     | Added when the first email is sent                                   |

Preview deployments do not get `DATABASE_URL`, so they never touch the production database. Local development keeps using the Docker database from `.env.development`, which holds no production values.

---

## Migrations

- The ERM keeps its migration history in the `erm_migrations` schema. The website keeps its own in `drizzle.__drizzle_migrations`. Neither app reads the other's history.
- On a production deploy of the `main` branch, `vercel.json` runs the migrations before the build. A failed migration stops the deploy, so the old version keeps running.
- Nobody runs migrations against production from a laptop, and nobody edits the production database by hand.
- Migrations only add tables and columns the ERM owns. They never touch the website's tables.

---

## Website tables the ERM reads

| Table                               | Service track |
| ----------------------------------- | ------------- |
| `custom_engineering_submissions`    | Tier 1        |
| `drafting_digitization_submissions` | Tier 3        |

Each row has a `request_id` such as `T1-1789787898386`. The ERM uses it as the project's request ID. The other website tables are not project intake.
