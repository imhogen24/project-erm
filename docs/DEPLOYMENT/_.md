# Deployment

How the ERM runs in production. Setup for development is in the root `README.md`.

---

## Where it runs

- The app runs on Vercel.
- The database is Neon. The company website uses the same Neon database, so the ERM reads the website's intake tables directly. There is no webhook.
- Email is sent with Resend, from the verified company domain.

---

## Environment variables

Production does not use dotenvx. The values are plain variables in Vercel (Settings, Environment Variables), set for Production only:

| Variable             | What it is                                                           |
| -------------------- | -------------------------------------------------------------------- |
| `DATABASE_URL`       | The Neon connection string                                           |
| `BETTER_AUTH_SECRET` | A long random secret, different from development                     |
| `BETTER_AUTH_URL`    | The public address of the app, for example `https://erm.example.com` |
| `RESEND_API_KEY`     | The Resend key. Never set in development. Missing in production, every email fails |
| `EMAIL_FROM`         | The sender, `noreply@admin.imhogen.com`, verified in Resend          |
| `INNGEST_SIGNING_KEY` | Inngest's signing key. `/api/inngest` refuses any request not signed with it |
| `INNGEST_EVENT_KEY`  | Inngest's event key, for sending events to Inngest                  |

Preview deployments do not get `DATABASE_URL`, so they never touch the production database. They do not get the Inngest keys either, so `/api/inngest` answers "Inngest is not configured." there. Local development keeps using the Docker database from `.env.development`, which holds no production values.

## Migrations

- The ERM keeps its migration history in the `erm_migrations` schema. The website keeps its own in `drizzle.__drizzle_migrations`. Neither app reads the other's history.
- On a production deploy of the `main` branch, `vercel.json` runs the migrations before the build. A failed migration stops the deploy, so the old version keeps running.
- Nobody runs migrations against production from a laptop, and nobody edits the production database by hand.
- Migrations only add tables and columns the ERM owns. They never touch the website's tables.

## Website tables the ERM reads

| Table                               | Service track |
| ----------------------------------- | ------------- |
| `custom_engineering_submissions`    | Tier 1        |
| `drafting_digitization_submissions` | Tier 3        |

Each row has a `request_id` such as `T1-1789787898386`. The ERM uses it as the project's request ID. The other website tables are not project intake.

- The ERM only reads these tables. Their read-only definitions are in `db/website/schema.ts`, outside `db/schema`, so the ERM's migrations never create or change them. A test fails if ERM code writes to them.
- The file column is `file_attachments` on Tier 1 and `file_attachment` on Tier 3. Each entry is a plain link.
- The client's files stay in UploadThing. A record keeps each link exactly as the website saved it, and the ERM never copies the files. A person opens one through `GET /api/files/[recordId]?ref=<link>`, which sends them to the link only when they may read the record and the link is stored on it. Anything else gets not found. The links are public, so this controls what the ERM hands out, not who can open a file.
- When a request is pulled in, the ERM saves its own copy in `intake_submissions`: the request ID (unique), the service track, the whole website row as JSON exactly as read, the time it arrived, and the project once it is created. A request with a copy is never pulled in again. `findNewSubmissions` and `copySubmission` are in `server/intake/`.
- `pullNewRequests` in `server/intake/intake.ts` pulls in every new request, oldest first, each in its own transaction: the copy, a project named from the request, and a D1.1 draft created by the system person, with the request status Pending and one Pending row per file link. Every company-wide IT/Admin gets a `new_request` dashboard notification and, once the request is saved, a `new_request` email. A request that fails saves nothing and is tried again on the next run. A request ID that already has a project only links the copy to it. It returns request IDs only. The tools must be registered before it runs (`ensureToolsRegistered` in `lib/tools.ts`), and email links start with `BETTER_AUTH_URL`.
- Development and tests use empty local copies of the two tables, made by `db/website/local.ts` in the test setup and in `bun run db:reset`. It refuses any database that is not local.
- Nothing from these tables goes into a log or an error message.

## Scheduled intake

- Inngest runs `intake-run` (`server/inngest/intake-run.ts`) every 5 minutes. It calls `pullNewRequests`, so a new website request becomes a project within minutes. Inngest reaches it through `/api/inngest`, which only serves requests signed with `INNGEST_SIGNING_KEY`.
- A request that cannot be pulled in is reported in the run's summary by its request ID, and the run still succeeds.
- A run that throws is retried three times, with a growing delay. If it still fails, every company-wide IT/Admin gets an `intake_failed` dashboard notification, at most once every 6 hours. Inngest's dashboard shows the failed run.
- Only one run works at a time. A run that is still going makes the next one wait.
- The run's error and the notification never hold a client's details.

### Running it locally

1. Start the app in Inngest's dev mode: `INNGEST_DEV=1 bun dev`.
2. In a second terminal, start the Inngest dev server: `bunx inngest-cli@latest dev -u http://localhost:3000/api/inngest`.
3. Open `http://localhost:8288` to see `intake-run`, its runs, and to trigger it by hand.
