# UI context

How every screen in the ERM looks and behaves. Read this before you build or
change a screen, and load the `frontend-design` skill. The rules here are
decisions already made; follow them before inventing anything new. When a rule
here and a skill disagree, this file wins.

The live reference is the code named in each section. If a pattern you need is
missing, add it to the shared place (a CSS variable or class in
`app/globals.css`, or a component in `components/`) and add a line here.

**Keeping this file true.** Read it in full before any UI work. Every UI
decision, whether the user's choice, a correction they give or a new shared
pattern, is written here in the same change that makes it, with the code it
lives in. When a decision replaces a rule, change or remove the old rule so
the file never contradicts itself. A decision that is only in code or in chat
is not made.

## 1. Layout

- **The drafting grid.** Every page sits on `.drafting-grid`. Its lines are
  muted (`--grid-major`, `--grid-minor`) so they never compete with the
  content, and a box's outline (`--rule`) is the same colour as a major line.
  On wide screens the sidebar and page sit one small square (`--inset`) from
  the top and bottom of the screen. One major square
  is `--cell` (96px from 640px up), and a small square (`--small`) is a
  quarter of it. The grid is centred: the leftover width is split between the
  two sides.
- **Sidebar and page.** The screen is for working, so on wide screens the page
  takes every square it can. The sidebar (`.sidebar-frame`) is three squares
  wide, one small square in from the left. The page (`.table-project` or
  `.table-wide`) starts one small square after it and runs to the last
  small-square line that leaves at least one small square on the right. Every
  edge stays on the paper's lines (`--grid-start`).
- **One sheet per page.** Draw every page with `PageSheet`
  (`components/page-sheet.tsx`): title over a ruled line, then the body, at
  least as tall as the sidebar. Page-wide buttons go in its `actions` slot, at
  the right of the title. Tool pages use `ToolSheet`: a top bar
  (`RecordTopBar`) with the project, the tool's title and state badge and the
  document control, then the sheet with only the tool's tables, as two boxes one small square apart.
  The document control is one slim row of facts, each as wide as its text,
  on the sheet's own paper (no filled cells). On a wide screen the top bar is
  pinned level with the sidebar on a
  `.paper-mat`, so the document control stays in view while the sheet scrolls
  under it.
- **Tiles fill the sheet.** A grid of tiles uses `flush` and shares the
  sheet's lines; rows share spare height so no empty strip is left at the
  bottom (see `app/(app)/page.tsx`).
- **Full width.** No empty right half. No `max-w-*` that leaves a blank column
  inside a sheet.
- **Mobile first.** Nothing scrolls sideways at 375px. Rows of a table become
  stacked cards on narrow screens.

## 2. Colour and tokens

- Use the CSS variables in `app/globals.css`. Never a one-off value such as
  `bg-foreground/[0.04]`, `bg-primary/20` or a raw hex in a component.
- Surfaces: `--surface-tile`, `--surface-tile-hover`, `--surface-chosen`,
  `--surface-note`, `--surface-inset`. Chips: `--chip-open`, `--chip-done`.
  Borders of fields: `--input`.
- Colour means something, the same thing everywhere:
  - **Orange** (`--primary`): needs action, or chosen, or good (a tick).
  - **Red** (`--destructive`): failed or refused.
  - **Grey**: everything else.
- Check light and dark. A token must read in both; never fix one theme with a
  colour that breaks the other.

## 3. Shapes and borders

- Grid boxes, sheets and tables are square (`--radius: 0`).
- Controls are softly rounded with `--radius-control`: buttons, fields,
  selects, chips, badges, tiles, avatars. Never a circle unless it is a radio,
  a dot or a count.
- No borders inside a grid square. Set things apart with a fill
  (`.tile`, `.note-panel`, `.inset-row`), not a frame inside a frame.
- To tint a box that draws grid lines with shadows, use a background layer,
  never `box-shadow`.

## 5. Controls and forms

- **Columns as wide as what they hold.** A column's width follows its
  content (`lib/column-widths.ts`): an SN or serial number is narrow, a short
  answer (a number, a percentage, Yes/No) takes less than a share, a choice,
  date or amount one share, short text one and a half, and long text the
  most. A column that holds only a button is as wide as the button. Tool
  tables size themselves from their column types; other tables pass
  `widthsOf([...])` to `DataTable`. Never split a table into equal columns
  that leave a serial number wide and the text squeezed.
- **One look for every row.** A row the app fills in and a row the person
  adds look the same: same fill, same text size. A fixed cell is marked only
  by its padlock. No row, cell or block gets a lighter fill to set it apart:
  not a fixed cell, a subtotal row, an instruction or "Not signed yet".
- **Every column has a name.** A header cell is never left blank, with one
  exception: the Remove column. Buttons that act on a row's document (View,
  Download) sit in that document's cell, at the right of its name, not in a
  column of their own.
- **Remove has its own column.** In a table where some row can be removed,
  the Remove buttons get a narrow column at the right (`TableEditor`), so the
  fields of every row line up. A table whose rows all stay has no such
  column.
- **View buttons line up.** Every View button is one small size (`viewButton`
  in `components/pdf-preview-field.tsx`) and sits at the right of its cell,
  after the document's name, so a column of them reads as one straight line.
  A document that cannot open shows View disabled; why ("Not started", "No
  access", "Not needed") is said only on hover and to a screen reader, never
  as text beside the button.
- **Values the app works out read as text.** A total, an amount or anything
  copied in from another tool shows as text with no box (`.system-input`),
  even though it is still an input so its label names it. An empty one shows
  "-", unless its definition gives a `systemNote` saying when it fills in.
- **A signature is a row of its section.** A signature that belongs to a
  section is one more row of that section's table, with Sign at the right of
  its answer, so the section is one box under one title. A signature with no
  section is a box of its own.
- **One badge size.** Every badge and chip (shadcn `Badge`, `.state-badge`,
  `.status-chip`) is `--badge-height` tall with `--badge-text` and
  `--badge-padding`, whatever its colour, so badges side by side line up.
- **One height.** Fields, selects and the button beside them are
  `--control-height` (48px). In a table row every field starts one line tall
  and the row reads level; a long answer grows as it is typed.
- **Selects** open below the field at its width, on a solid surface. Rich
  options use `OptionRow`, and the chosen option shows the same way in the
  closed field.
- **Choices show their meaning.** The chosen option fills with what it means
  (Pass orange with a tick, Fail red with a cross). Never a grey fill that
  says nothing.
- **Locked means read.** On a locked record, fields, selects and dates read
  as plain text with no box, caret, icon or placeholder; the chosen option
  stays bright and the others fade. Add row and Remove do not show.
- **No hint that repeats a label.** If a column or label already names the
  field, leave the placeholder out.
- **Labels and names stay stable.** Keep accessible names (`aria-label`,
  button text) when you restyle; the e2e tests find controls by them.

## 6. Behaviour

- **A tile that opens something opens from anywhere on it.** Use
  `.stretched-link` (or `.tile-cover` when the visible link is a button) on a
  `.link-tile`. Controls inside sit above it with `.above-stretch` or
  `.above-stretch-row`. The whole tile tints on hover and shows focus.
- **What cannot be used is not a link.** A tool that cannot open yet is
  greyed, says what it waits on, and its address leads back to the project.
- **One project tier.** A Tier 1 project never shows a T3 tool; a Tier 3
  project shows the T3 tool in place of the one it replaces.
- **Keyboard and motion.** Every control is reachable by Tab with a visible
  focus ring. Motion respects `prefers-reduced-motion`.

## 7. Words

- Sentence case. No all-caps labels, no label above every heading.
- Name things the way the person knows them: the role in full where it helps
  ("PM Project Manager"), the operand's name under its letter.
- A button says what happens: "Submit for approval", "Create invite",
  "Assign". The same action keeps the same name everywhere.
- An empty state says what to do next ("Nothing here yet. Press Add row to
  start the list."). Every empty result uses `EmptyState`, never a bare line
  of grey text: `page` where the empty result is the whole page or panel,
  `inline` inside a table or box. Its drawing is `gear` for work not started,
  `flange` for an empty list and `bracket` for nothing that fits.
- Errors say what went wrong and how to fix it. They do not apologise.
- Do not explain the system to the person. Leave out lines that describe how
  the screen works or what the system does on its own ("Edits save by
  themselves.", "This record is read only.", "Filled in by the system"
  everywhere). The screen shows it: a badge, a disabled field, the missing
  button. Say something only when the person must act on it or would
  otherwise miss it: a save that failed, what stops a button, a result they
  asked for ("✓ Saved", "Sent.").
- Do not invent facts. Labels, role titles and option names come from the
  definitions or `docs/`; if they are not there, ask.

## 8. Before you say it is done

1. Typecheck and lint pass.
2. Look at the screen in a browser: light, dark, and 375px wide.
3. Check nothing overlaps, sticks out of its cell, or scrolls sideways. In
   every table: SN is narrow, no text or choice is cut off, every row looks
   the same, and buttons in one column line up.
4. Check every new colour, radius and size uses the tokens and shared parts
   above.
5. Add the screen to `scripts/db/preview.ts`: who to log in as, the route, what
   should be there. Then run `bun run accounts:doc` to update
   `docs/TEST_ACCOUNTS/_.md`.
6. Make sure the seed data shows the screen with realistic content
   (`scripts/db/seed-data/`); no "Demo" names.
7. Tell the user who to log in as and which route to visit.
